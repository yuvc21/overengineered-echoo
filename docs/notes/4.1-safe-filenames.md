# 4.1 Safe filenames (path traversal)

> **Status:** done | **Area:** `src/http_parser.cpp`

## What is happening

The server serves files from one folder, given by `--directory`. A request like `/files/hello.txt` makes the server look for `hello.txt` inside that folder. A client can send a trick filename like `../etc/passwd`, where `..` means "go up one folder". The server then ends up reading, or writing, a file **outside** the folder it was meant to stay in. This attack is called **path traversal**.

## Why it happens

The filename comes straight from the client, and the server simply joins it to the directory path. It never checks whether the name is a plain filename or a path with folder jumps in it. The operating system happily follows `..` and `/`, so the final path can point anywhere the server process has access to.

## What was done to prevent it

A check was added so that a filename is accepted only if it is a single plain name. It is rejected if it is:

- **empty**, because it would point at the directory itself
- **`.` or `..`**, the "current folder" and "parent folder" entries
- **containing `/` or `\`**, because that turns the name into a path with folders
- **containing a NUL byte**, because C functions stop reading at NUL, so `x.txt\0.png` could be treated as `x.txt`

The check runs for both GET and POST on `/files/`, and any unsafe name gets `400 Bad Request` before the filesystem is touched.

## Benefits of the fix

- The server can only reach files inside the served folder.
- Safe to expose publicly on Cloud Run.
- Bad input is rejected early with a clear status code.
- Simple allow-list rule that is easy to reason about and test.

## Losses if not fixed

- **Data leak:** anyone could read system files such as `/etc/passwd`, config files, or secrets stored in the container.
- **Data tampering:** with POST, anyone could write or overwrite files outside the folder, including the server's own files.
- **Public exposure:** once deployed, the attack takes one `curl` command from anywhere on the internet.
- **Credibility:** path traversal is a well-known vulnerability, and shipping it reflects badly on the project.

## Remember

- Never trust client input when building a filesystem path.
- Allow only a plain name instead of trying to clean up bad ones.
- POST traversal (write) is worse than GET traversal (read).
